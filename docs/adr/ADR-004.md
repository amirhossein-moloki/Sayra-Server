# ADR-004: Database

## Context
The Central Backend requires a database engine that guarantees absolute transactional safety (ACID) for financial billing, concurrent player sessions, and critical system audits, while also supporting unstructured telemetry log data.

## Decision
We select **PostgreSQL (v16+)** as our primary relational database.

## Alternatives Considered
1. **Microsoft SQL Server**: Excellent, but introduces licensing costs and complex platform dependencies.
2. **MySQL / MariaDB**: Decent, but historically lacks the advanced SQL query optimization, robust MVCC, and rich JSON indexing capabilities of PostgreSQL.
3. **MongoDB**: Highly scalable document store, but highly prone to integrity issues for complex financial calculations and multi-table transactions.

## Reasons
* Strong ACID transaction compliance, which is crucial for financial and auditing modules.
* Outstanding open-source support with zero licensing or scaling cost limits.
* Industry-leading support for semi-structured data via the **JSONB** column type and GIN indexes, allowing efficient storage of raw telemetry and command audits in the same relational engine.
* Deep integration with EF Core through the mature, highly-optimized `Npgsql` provider.

## Consequences
* Every module will define its schema migrations within PostgreSQL.
* Deployment environments will provision a PostgreSQL instance, either standalone or inside Docker Compose.

## Risks
* Unoptimized queries or lack of appropriate indexing could cause database locking, impacting real-time performance.
* High-volume telemetry writes could bloat the database if a strict rotation/downsampling policy is not established.

## Migration/Evolution Strategy
To support horizontal scaling, we can leverage PostgreSQL connection pooling (`PgBouncer`), read-replicas, or divide database schemas into separate physical database servers (database-per-module) without modifying application code.
