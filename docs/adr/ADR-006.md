# ADR-006: Redis

## Context
With thousands of persistent TCP connections, the backend needs a high-performance cache, a distributed locking mechanism, and a real-time message broker to synchronize state and route commands across horizontally scaled monolith nodes.

## Decision
We select **Redis (v7+)** as our centralized distributed state cache, lock manager, and real-time Pub/Sub backplane.

## Alternatives Considered
1. **Memcached**: Excellent cache, but lacks Pub/Sub capabilities, data persistence, streams, and rich data structures (Hashes, Sets, Lists).
2. **PostgreSQL-backed Locks**: Possible, but introduces high database polling overhead and slower response times compared to memory-speed Redis locks.

## Reasons
* Outstanding performance with sub-millisecond latencies for caching and state tracking.
* Rich data structures (Hashes, Sorted Sets, Lists, Streams) allow sophisticated state management.
* High-performance Pub/Sub engine allows real-time TCP command routing between different cluster nodes.
* Robust distributed lock implementation (`RedLock` pattern via StackExchange.Redis) ensures session or billing operations are never duplicated concurrently.

## Consequences
* The application will require a connection to Redis.
* Ephemeral states (workstation online status, active connection nodes, rate limiting, temporary sessions) will be managed via Redis.
* Ephemeral keys will always be set with explicit Time-To-Live (TTL) expirations to prevent Redis memory exhaustion.

## Risks
* Redis is an in-memory database. A crash could wipe transient session states unless persistence (AOF/RDB) is configured.
* Over-reliance on Redis as a primary database could lead to data loss (financial calculations must never treat Redis as the authoritative source of truth).

## Migration/Evolution Strategy
Redis will be deployed in a clustered or Sentinel configuration for high-availability staging and production environments. Core business logic will gracefully handle Redis disconnects by using PostgreSQL fallback or local memory fallback caches where appropriate.
