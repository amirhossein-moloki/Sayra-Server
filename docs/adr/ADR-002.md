# ADR-002: Backend Framework

## Context
The Central Backend must expose RESTful APIs, manage WebSocket/SignalR real-time hubs, host custom TCP/UDP server backends, and run recurring background workers within a unified, highly-testable package.

## Decision
We select **ASP.NET Core (Web API / Minimal APIs)** under .NET 8.0.

## Alternatives Considered
1. **Express / NestJS (Node.js)**: Simple, but lacks native compilation guarantees and performance characteristics of ASP.NET Core under high load.
2. **Gin / Fiber (Go)**: Very fast, but lacks a complete built-in ecosystem for dependency injection, secure configurations, and rich testing.
3. **Spring Boot (Java)**: Highly mature, but significantly heavier, uses more memory, and has slower startup times compared to .NET 8.

## Reasons
* Includes built-in, industry-standard Dependency Injection (DI), robust configuration providers, logging integrations, and middleware pipelines.
* Built-in support for Kestrel, a high-performance web server that excels at raw HTTPS, WebSockets, and TLS termination.
* Exposes **Minimal APIs** which drastically reduce boilerplate code for small, high-throughput endpoints.
* Exceptional testing utility via `WebApplicationFactory`, allowing in-memory integration testing of HTTP routes, dependency overrides, and security filters.

## Consequences
* Application bootstrapping will follow the modern ASP.NET Core `Program.cs` structure.
* Dependency registration and lifecycle controls (Transient, Scoped, Singleton) will be strictly enforced through the native IoC container.

## Risks
* Improper middleware configuration could introduce performance bottlenecks.
* Large monolithic API route catalogs can become messy if not structured into clean, module-specific route registries.

## Migration/Evolution Strategy
APIs are decoupled from core domain logic using the mediator or event pattern. If we extract a module into a microservice, its Minimal API route registrations can be cleanly moved to a lightweight independent ASP.NET Core project.
