# ADR-011: Observability

## Context
Diagnosing real-time TCP network issues, command latencies, and distributed job execution in a multi-protocol monolith requires unified, structured monitoring across HTTP, TCP, and background tasks.

## Decision
We implement **OpenTelemetry** with structured logging (via **Serilog**), metrics, and distributed tracing.

## Alternatives Considered
1. **Plain text console logging**: Extremely hard to parse or search at scale.
2. **Proprietary Monitoring Agents (NewRelic, Datadog)**: High licensing costs, and they often require active internet connections, which violates our offline-first LAN constraint.

## Reasons
* **Open Standard**: Supported by almost all modern APM tools (Jaeger, Prometheus, Grafana, OpenSearch).
* **Structured Logs**: Serilog exports JSON-formatted logs with dynamic property context (e.g., `WorkstationId`, `SessionId`), making them instantly searchable in tools like Loki or Elastic.
* **Correlated Diagnostics**: We can trace a single action (e.g., administrator clicks a button in the Web UI) through the REST controller, into the EventBus, out onto the TCP Socket, and back as a client response, mapped to a unified `TraceId`.

## Consequences
* Every HTTP request, background worker loop, and TCP connection handshake will automatically spin up or propagate a trace context.
* Code will output structured log strings like `LogInformation("Starting session {SessionId} for client {ClientId}", sessionId, clientId)`.

## Risks
* High tracing volume can lead to heavy log file bloat and storage resource consumption.
* Logging sensitive payload data (passwords, JWT tokens) must be prevented via log sanitization filters.

## Migration/Evolution Strategy
Our local logging and telemetry outputs will write to files or standard output inside containers. Administrators can run a lightweight, local observability stack (Grafana, Loki, Prometheus) alongside Docker Compose if deep diagnostic monitoring is requested.
