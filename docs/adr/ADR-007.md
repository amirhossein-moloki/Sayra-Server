# ADR-007: Background Processing

## Context
The Central Backend must execute recurring maintenance tasks, process telemetry reports asynchronously, handle timeout events (heartbeats, commands), and perform cleanups without blocking critical client-facing REST APIs or TCP socket layers.

## Decision
We select ASP.NET Core **Hosted Services (IHostedService / BackgroundService)** backed by PostgreSQL/Redis for reliable task management.

## Alternatives Considered
1. **Hangfire**: Excellent dashboard and queue management, but requires a heavy database footprint and introduces complex schema-coupling to our database engine.
2. **RabbitMQ / Celery**: Robust distributed job processors, but introduces excessive infrastructure and operational overhead for a local gaming center deployment.
3. **Quartz.NET**: Highly mature scheduler, but overly complex for simple interval-based tasks and asynchronous processing queues.

## Reasons
* In-the-box ASP.NET Core native integration (`BackgroundService`) with zero external dependency costs or deployment overhead.
* Light memory footprint and fully integrated with the native Dependency Injection (DI) lifecycle.
* Combined with a **Redis List/Stream** or a PostgreSQL queue table, we can easily build resilient, persistent background task queues.
* Fully supports asynchronous cancellation tokens for graceful server shutdowns.

## Consequences
* Background workers will be registered in `Program.cs` and run concurrently within the Monolith host process.
* Thread counts and task concurrency will be configured safely to prevent resource starvation of the HTTP/TCP listeners.

## Risks
* If the monolith process crashes, in-memory tasks are lost (mitigated by storing persistent job state in PostgreSQL/Redis before dispatching).
* Long-running background jobs could block process shutdown (mitigated by respecting `CancellationToken` in loop conditions).

## Migration/Evolution Strategy
If background job processing needs to scale independently of the web API, we can compile the Monolith project with only the background worker registrations active and run it as an independent worker container scaling horizontally.
