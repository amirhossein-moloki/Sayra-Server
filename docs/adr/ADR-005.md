# ADR-005: ORM / Data Access

## Context
The Central Backend must perform safe, productive, and maintainable database access while preventing SQL injection vulnerabilities. We need robust migration tracking and compile-time check guarantees for database queries.

## Decision
We select **Entity Framework Core 8 (EF Core 8)** as our primary Object-Relational Mapper (ORM).

## Alternatives Considered
1. **Dapper**: A lightweight micro-ORM offering exceptional performance, but requires writing manual SQL queries, handling mappings manually, and lacks schema migration management.
2. **ADO.NET Raw Sockets**: Too low-level and highly verbose, drastically slowing down business feature velocity.

## Reasons
* Offers compile-time safe querying using LINQ, preventing a huge class of runtime SQL syntax errors.
* Integrated migration management toolchain, allowing schema versions to be tracked in Git and applied safely across Staging and Production.
* Supports **Global Query Filters** out-of-the-box (ideal for multi-site/tenant isolation).
* EF Core 8 performance has been optimized to match near-raw ADO.NET speeds for most typical queries.

## Consequences
* Every module will declare its own `DbContext` that registers only the database tables owned by that specific module.
* DB context configurations will be encapsulated inside the module's assembly.

## Risks
* Heavy queries or accidental "N+1" query loading can hurt application latency.
* Overuse of tracking queries can bloat memory usage (mitigated by enforcing `.AsNoTracking()` for read-only queries).

## Migration/Evolution Strategy
For extremely high-performance telemetry ingestion or critical reporting pipelines, we allow developers to fall back to **Dapper** or raw SQL queries within the specific module's repository layer.
