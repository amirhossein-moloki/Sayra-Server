# ADR-010: Deployment Architecture

## Context
SAYRA must support seamless local-LAN operations, rapid testing, and robust staging/production parity. The deployment must be simple enough for local network administrators to manage without complex cloud orchestration.

## Decision
We select **Docker Compose** as our standard multi-platform containerization and deployment orchestrator.

## Alternatives Considered
1. **Kubernetes (K8s)**: Outrageously complex and highly resource-intensive for small LAN gaming centers. Introduces massive configuration overhead.
2. **Bare-Metal OS Installation**: Highly prone to environment drift (different .NET runtimes, missing OS patches, port conflicts), making updates and troubleshooting extremely difficult.

## Reasons
* Provides true cross-platform portability. The exact same container runs on developer machines, QA staging environments, and production servers.
* Allows declaring the entire stack (Monolith, PostgreSQL, Redis) in a single declarative `docker-compose.yml` file.
* Light on system resources and extremely easy to troubleshoot using standard commands (`docker compose logs -f`).
* Simplifies software updates; updating the backend is as easy as pulling a new image and running `docker compose up -d`.

## Consequences
* The Central Backend project will contain a multi-stage `Dockerfile` optimizing build sizes and maximizing security (using Alpine or Distroless base runtimes).
* Local deployment guides will focus entirely on Docker Compose configurations.

## Risks
* Local network administrators must have Docker/Docker Compose installed on their host systems.
* Improper Docker host storage volume mapping could lead to database data loss on container restarts (mitigated by explicit volume mount rules).

## Migration/Evolution Strategy
If the backend transitions to a cloud-hosted, multi-tenant SaaS platform, these Docker containers are 100% ready to run in managed container engines like AWS ECS, Azure Container Apps, or Kubernetes without modifying their contents.
