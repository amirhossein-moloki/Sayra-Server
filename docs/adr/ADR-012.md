# ADR-012: Scalability Strategy

## Context
As gaming centers grow, a single backend process may eventually struggle to handle high-frequency telemetry, database writes, and persistent TCP connections. We need a clear, incremental scaling path.

## Decision
We scale horizontally by running **multiple Monolith worker nodes** behind a **stateless TCP/HTTP load balancer**, routing operations and state updates asynchronously via a **Redis shared state cache** and **Redis Pub/Sub network**.

## Alternatives Considered
1. **Vertical Scaling Only**: Simply running on bigger servers. Extremely simple, but has a hard physical ceiling and creates a single point of failure (no high availability).
2. **Premature Microservices separation**: Splitting into microservices on day one. Increases development friction dramatically without solving the fundamental TCP state distribution challenge.

## Reasons
* Allows horizontal scalability of standard Monolith instances without complex database sharding.
* Utilizes **Redis** to keep a distributed list of active client TCP sockets and workstations online states.
* Enables any backend node to route commands to any client workstation regardless of which physical node holds the active TCP connection tunnel (using **Redis Pub/Sub**).
* Ensures database transactional scalability by utilizing background task buffering and high-performance Postgres connection pooling.

## Consequences
* Workstations are assigned unique IDs. When Node A wants to send a command to Workstation 12, it looks up where Workstation 12 is connected in Redis.
* If connected to Node B, Node A publishes to `workstation:commands:12` via Redis Pub/Sub, and Node B delivers it down the active TCP connection.

## Risks
* Introduces a hard dependency on Redis for high-availability scaling (if Redis dies, cluster nodes cannot coordinate).
* Dynamic load balancing of raw TCP sockets can lead to uneven connection distributions if not configured with least-connection algorithms.

## Migration/Evolution Strategy
Our architecture scales gracefully from single-instance (zero Redis clustering overhead) to high-concurrency multi-node environments simply by toggling standard configuration files, keeping deployment incredibly flexible.
