# ADR-003: Monolith vs. Microservices

## Context
Choosing the operational and development topology for the Central Backend. It must run reliably in local, offline-first LAN gaming centers while supporting rapid feature iterations and scaling to thousands of client workstations.

## Decision
We select a **Modular Monolith** architecture.

## Alternatives Considered
1. **Microservices (Option B)**: Separate services for everything (Billing, Workstations, Sessions). Highly complex, introduces massive network overhead, distributed transaction issues, and is impractical for LAN gaming centers to self-host.
2. **Hybrid Monolith (Option C)**: Part monolith, part microservice. Too complex for initial phases; introduces operational overhead without immediate benefits.

## Reasons
* **Operational Simplicity**: Gaming centers require an "offline-first" server. Deploying and managing a single unified backend process via Docker Compose is incredibly easy compared to coordinating 10+ microservices.
* **Consistency**: Avoids distributed transaction issues (Sagas, 2PC) for core operations like workstation allocation and session charging.
* **Low Network Overhead**: Modules communicate in-memory, ensuring ultra-low latency.
* **Clear Path to Growth**: By enforcing strict module separation (no shared tables, communicating via interfaces/events), we can cleanly extract any module into an independent microservice later if needed.

## Consequences
* The codebase will be organized into logical modules. Each module will have its own folders/projects representing its Data, Logic, and API layers.
* Cross-module schema querying is prohibited. All cross-module operations must go through Public Interfaces or the Event Bus.

## Risks
* Without automated architectural tests (such as `ArchUnitNET`), developers might accidentally introduce illegal cross-module direct assembly references, creating a "spaghetti" monolith.
* A fatal crash (e.g., OutOfMemoryException) in one module will crash the entire application process.

## Migration/Evolution Strategy
We will implement automated architectural guardrails using ArchUnitNET to enforce compilation-level boundaries. If a module (e.g., Telemetry) requires distinct scaling, we can easily extract it since its data and interfaces are already fully isolated.
