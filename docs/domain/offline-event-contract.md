# Canonical Offline Event Contract & Event Classification (Phase 09 - Stage 09-01)

## Executive Summary & Architecture Scope

This document establishes the authoritative, canonical **Offline Event Contract and Event Classification** for the SAYRA Central Backend and SAYRA Client ecosystem.

During Central Backend disconnection, the SAYRA Client retains business and operational events durably in local encrypted storage. Upon reconnection, the client securely, ordered, idempotently, and auditably reconciles them with the Central Backend.

---

## 1. Core Principles & Boundaries

### Non-Negotiable Guarantees
1. **At-Least-Once Delivery**: Every queueable event generated by the client during online or offline modes will be delivered to the Central Backend at least once.
2. **Idempotent Server Processing**: The Central Backend handles duplicate submissions without producing duplicate business or financial side effects.
3. **Server Authority**: Central Backend remains the absolute authority for business logic, pricing, financial ledgers, session validation, and workstation states. Client events are submitted as *evidence* of offline occurrences.
4. **Durable Client Queue**: Offline events are persisted in durable, crash-resilient encrypted local storage (SQLCipher/SQLite) prior to transmission.

### Cross-Phase Boundary Isolation
* **Phase 03 / 05 (Sessions, Workstations, Pricing, Financials)**: Session lifetime and workstation operations submitted offline are reconciled against authoritative domain services (`SessionManager`, `FinancialAccountService`).
* **Phase 06 (Configuration Management)**: System configuration remains strictly Server-authoritative. Phase 09 does not create parallel configuration synchronization mechanisms.
* **Phase 07 (Software Updates)**: Software update package delivery and release lifecycles retain existing contracts.
* **Phase 08 (Telemetry & Observability)**: Phase 08 owns high-frequency telemetry metrics (`Cpu`, `Ram`, `Uptime`, `HEARTBEAT`). Phase 09 provides reliable queueing **only** for discrete business and operational events.
* **Security & Transport**: Phase 09 reuses existing TLS 1.3 TCP framed sockets, `SecureMessageEnvelope` HMAC-SHA256 encryption, and authenticated connection identities (`ITcpConnection.PcId`).

## 3. Reliability Classification Taxonomy

Every event is assigned a explicit priority/reliability class governing its queueability, persistence, ordering, retention, and overflow policies.

| Reliability Class | Applicable Event Types | Queue Offline? | Priority Level | Ordering Requirement | Retention Period | Overflow Policy | Business Consequence of Loss |
|---|---|---|---|---|---|---|---|
| `CRITICAL` | `SESSION_COMMAND_REQUEST`, `SESSION_RUNTIME_EVENT`, `SECURITY_EVENT` | **Yes** | 1 (Highest) | Strict Monotonic (`SequenceNumber`) | 30 Days | Reject new non-critical events; preserve `CRITICAL` in SQLCipher | Loss of billing accuracy, uncharged usage, unrecorded security breaches |
| `IMPORTANT` | `CLIENT_STARTED`, `CLIENT_STOPPED`, `WORKSTATION_STATE_CHANGED`, `APPLICATION_CRASHED`, `CONFIGURATION_CHANGED` | **Yes** | 2 | Per-Workstation Monotonic | 7 Days | Retain in queue; drop `NORMAL` events if capacity exceeds 80% | Loss of workstation lifecycle tracking and crash diagnostics |
| `NORMAL` | `APPLICATION_STARTED`, `APPLICATION_EXITED`, `DEVICE_CHANGED`, `NETWORK_CHANGED`, `DIAGNOSTIC_EVENT` | **Yes** | 3 | Best-Effort / Timestamp | 24 Hours | FIFO eviction when queue reaches capacity limit | Minor gap in usage analytics or peripheral tracking |
| `EPHEMERAL` | `TELEMETRY`, `HEARTBEAT` | **No** | 4 | Latest-Wins Overwrite | Instantaneous (0s) | Drop immediately when offline | None; telemetry is transient point-in-time metrics |
| `NOT_QUEUEABLE` | `PONG`, interactive socket RPCs | **No** | N/A | Immediate Socket Frame | 0s | Reject frame if disconnected | N/A |

## 4. Telemetry vs. Business Event Boundary

Phase 08 owns high-frequency telemetry collection, metric aggregation, and health computation. Phase 09 owns offline queueing, synchronization, and durable delivery.

* **High-Frequency Metrics (`TELEMETRY`, `HEARTBEAT`)**: Classified as `EPHEMERAL`. When disconnected, these samples are **not queued** in SQLCipher. The client updates its local in-memory latest snapshot. Upon reconnection, only the latest telemetry frame is transmitted to avoid flooding the socket with stale CPU/RAM samples.
* **Business & Operational Signals (`SESSION_COMMAND_REQUEST`, `SECURITY_EVENT`, etc.)**: Classified as `CRITICAL` or `IMPORTANT`. These represent discrete state changes and MUST be durably queued.

## 5. Identification & Envelope Models

### Event Identifier (`EventId`) Forensics
* **Format**: String representation of a 128-bit GUID (`Guid.NewGuid().ToString("D")`).
* **Generation**: Generated on the client at the exact time of event occurrence, **prior to local database insertion**.
* **Immutability Invariant**: One logical event preserves its exact `EventId` across:
  `Client Creation → SQLCipher Local Queue → Sync Batch DTO → Secure Envelope Transport → Server Ingestion → Redis Deduplication → PostgreSQL AuditEvent → Audit Logs`.
* **Scope**: Globally unique.

### Sequence Number (`SequenceNumber`) Forensics
* **Scope**: Per-Workstation monotonic counter (`long`).
* **Generation**: Assigned by the client local queue engine during transactional insertion into SQLCipher.
* **Semantics**: Guarantees gap detection and deterministic reordering during offline sync batch reconciliation.

### Schema Versioning (`ContractVersion`)
* **Field**: `ContractVersion` (string, default `"1.0"`).
* **Policy**: Included in event envelopes. Allows Central Backend to maintain backward compatibility with older client versions.

## 6. Timestamp & Clock Semantics

1. `OccurredAt` (`ClientTimestamp`): Recorded by client using UTC (`DateTime.UtcNow`). Represents when the offline occurrence happened.
2. `ServerReceivedAt`: Recorded by Central Backend (`DateTime.UtcNow`) upon TCP message receipt.
3. `ProcessedAt`: Recorded upon database UOW commit.

### Clock Skew Rules
* The Central Backend server timestamp is authoritative for business state calculations.
* Client events with `OccurredAt` in the future (> 5 minutes ahead of `ServerReceivedAt`) are flagged with a clock skew warning.
* Client events with `OccurredAt` older than the retention threshold (e.g. 30 days for `CRITICAL`, 7 days for `IMPORTANT`) are rejected as `EXPIRED_EVENT`.

---

## 7. Identity Binding & Anti-Spoofing Contract

* **Authoritative Identity**: Derived strictly from the TLS 1.3 TCP authenticated session (`ITcpConnection.PcId` / `WorkstationId`).
* **Envelope Identity Validation**:
  * Every incoming `ClientEventEnvelopeDto` or `OfflineQueueItem` must match the connection's authenticated `PcId`.
  * If a client connected as `PC-001` submits an event payload claiming `ClientId = "PC-999"`, the Central Backend **rejects** the message and logs a `SECURITY_EVENT`.
  * **Rule**: Payload identity cannot override authenticated connection identity.

---

## 8. Client Storage Forensics (SQLCipher / SQLite)

The SAYRA Client utilizes SQLCipher / SQLite for local persistent storage.

### Queue Capability Requirements
* **Persistence**: Table `OfflineEventQueue` backed by encrypted SQLCipher file.
* **Transactionality**: Event insertion and queue status updates execute inside local database transactions.
* **Lifecycle Statuses**: `PENDING` → `IN_FLIGHT` → `ACKNOWLEDGED` (or `REMOVED`).
* **Index Strategy**: Indexed by `(Priority, SequenceNumber)` and `Status` to enable efficient priority batch extraction.
* **Crash Resilience**: Survives client process crash, OS reboot, and network drops. Unacknowledged events marked `IN_FLIGHT` reset to `PENDING` upon client restart.

| Domain / State | Client Authority | Server Authority | Server Reconciliation Preconditions |
|---|---|---|---|
| Session Start / Stop | Evidence (OccurredAt, Local Trigger) | **Absolute Authority** | Valid `SessionId`, `GamerId`, `WorkstationId`, `OccurredAt`, non-conflicting active session state |
| Session Duration & Cost | Consumed duration evidence | **Absolute Authority** | `SessionId`, active `PricingPlan` snapshot, server clock verification |
| Financial Balance & Payments | Evidence | **Absolute Authority** | Valid `AccountBalance`, `IdempotencyKey`, transaction ledger alignment |
| Workstation State | Hardware state evidence | **Absolute Authority** | `WorkstationId`, connection liveness state |
| System Configuration | No authority | **Absolute Authority** | Server `ConfigurationVersion` matching |

## 10. Idempotency & Conflict Categories

### Idempotency Model
* **Mechanism**: Dual-layer deduplication.
  1. **Redis Cache**: Key `v1:event:dedup:{EventId}` with 24-hour TTL.
  2. **PostgreSQL Database**: Unique index constraint on `AuditEvent.EventId` / `SecurityEvent.EventId`.
* **Behavior**: Duplicate delivery of an already processed `EventId` returns `Success = true` idempotently without re-applying business logic.

### Discovered Conflict Categories
1. `DUPLICATE`: Event with identical `EventId` already processed. Action: ACK idempotently.
2. `IDENTITY_MISMATCH`: Payload identity differs from TCP connection identity. Action: REJECT & log `SECURITY_EVENT`.
3. `SEQUENCE_GAP`: `SequenceNumber` gap detected in batch. Action: Process valid ordered contiguous prefix; request replay for missing range.
4. `EXPIRED_EVENT`: `OccurredAt` exceeds retention window. Action: REJECT & move to DLQ.
5. `STATE_CONFLICT`: Session action conflicts with server authoritative state (e.g. stopping an already terminated session). Action: SERVER_WINS; record audit reconciliation note.
6. `MALFORMED_PAYLOAD`: JSON payload failed contract schema validation. Action: REJECT & log error.

## 11. Offline Sync Protocol & ACK Semantics

### Message Lifecycle State Machine
```text
Client Event Triggered
       │
       ▼
SQLCipher Local Persistence (Status: PENDING)
       │
       ▼
Reconnection & Batch Creation (Status: IN_FLIGHT)
       │
       ▼
Encrypted TLS Framing (SecureMessageEnvelope)
       │
       ▼
Server Ingestion & Idempotent Processing
       │
       ▼
Server Sends OfflineBatchAcknowledgment (Success = true)
       │
       ▼
Client Deletes ACKed Items from SQLCipher Queue
```

### Failure Window Handling
* **Server Crashes before ACK**: Client retries sync batch on next reconnect. Server deduplicates via `EventId` and re-issues ACK.
* **ACK Lost on Network**: Client retries batch. Server recognizes duplicate `EventId`s and returns ACK idempotently. Zero duplicate business side effects.

---

## 12. Payload Constraints

* **Maximum Single Event Payload Size**: 256 KB.
* **Maximum Sync Batch Size**: 100 items or 2 MB total batch size per transport frame.
* **Compression**: Batches exceeding 64 KB may optionally use GZip compression before secure envelope encryption.

## 13. Canonical Contract Definitions

The canonical contract structures in C# (`Sayra.Backend.Contracts`) are defined as follows:

```csharp
public class ClientEventEnvelopeDto
{
    public string EventId { get; set; } = string.Empty;
    public string EventType { get; set; } = string.Empty;
    public string ClientId { get; set; } = string.Empty;
    public string WorkstationId { get; set; } = string.Empty;
    public string? SessionId { get; set; }
    public string CorrelationId { get; set; } = string.Empty;
    public long SequenceNumber { get; set; }
    public string ContractVersion { get; set; } = "1.0";
    public DateTime OccurredAt { get; set; }
    public string Payload { get; set; } = "{}";
}

public class OfflineQueueItem
{
    public string EventId { get; set; } = string.Empty;
    public string EventType { get; set; } = string.Empty;
    public long SequenceNumber { get; set; }
    public string ReliabilityClass { get; set; } = "NORMAL";
    public string ContractVersion { get; set; } = "1.0";
    public object Payload { get; set; } = null!;
    public DateTime Timestamp { get; set; }
}

public class OfflineBatchRequest
{
    public string BatchId { get; set; } = string.Empty;
    public string ClientId { get; set; } = string.Empty;
    public string WorkstationId { get; set; } = string.Empty;
    public List<OfflineQueueItem> Items { get; set; } = new();
}

public class OfflineBatchAcknowledgment
{
    public string BatchId { get; set; } = string.Empty;
    public int ProcessedCount { get; set; }
    public bool Success { get; set; }
    public List<string> AcknowledgedEventIds { get; set; } = new();
    public List<string> RejectedEventIds { get; set; } = new();
    public string? ErrorMessage { get; set; }
}
```
